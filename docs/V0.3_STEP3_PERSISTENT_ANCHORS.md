# V0.3 STEP 3 — Persistent Session Anchors

## What Changed

Taskify Anchors are no longer one-shot notices. A correctly bound activation now
returns the request lifecycle to `idle` while retaining the extracted Anchors as
Host-owned persistent state. Active Anchors continue to guide later model steps
in the same exact session until the user explicitly pauses, resumes, removes, or
clears them.

Request state and Anchor state are orthogonal. For example,
`request.phase = "idle"` with a non-empty `anchors` array is the normal persistent
state after activation.

## Scope

STEP 3 supports exact session scope only:

- the same session continues to receive its current active Anchors;
- a new session receives none;
- a child fork does not inherit parent Anchors, even when its seed history
  contains parent Taskify records;
- Taskify does not infer task completion or automatically expire an Anchor.

Every persistent Anchor carries `scope.kind = "session"` and the exact
`sessionId`. The source codec and replay fold reject records from another
session.

## Why No Goal Scope

The locally installed DSH `0.1.0-rc.6` public surface does not expose a supported
read API for a stable native Goal id, revision, or phase. Taskify therefore does
not parse `/goal`, consume undocumented goal events, or reimplement Goal state.
`goalIntegration.available` remains explicitly `false`.

## User Authority

Lifecycle authority is exposed only through explicit Client UI actions and the
corresponding Host Remote methods:

- `pauseAnchor`
- `resumeAnchor`
- `removeAnchor`
- `clearAnchors`

Each mutation requires `expectedRevision`, is checked with Host-side CAS, and
returns a complete authoritative snapshot. A stale revision returns
`revision-conflict`; the Client rehydrates with `getState()` and does not retry
the mutation silently. These operations are not Agent Tools, and the model has
no lifecycle mutation capability.

Lifecycle mutations are rejected with `request-busy` while a compile request is
`pending` or `armed`. This keeps the single revision stream and the activation
carrier's predeclared revision deterministic; the user can finish or invalidate
that request before changing existing Anchors.

## Persistent Lifecycle

### Activate

Compile creates one identified activation `UserMessage` in the Agent Inbox. On
the first exact human-draft match, `agent/pre-step` permits that same carrier,
changes the request from `armed` to `idle`, and additively merges its extracted
Anchors into persistent state. Exact `text + evidence` duplicates retain the
existing Anchor id and status. New ids are deterministic from bundle identity
and source index.

The persistent set is capped at 16 Anchors. A merge that would exceed the cap
fails visibly and atomically: no partial activation, eviction, or model-selected
deletion occurs.

### Pause

Pause keeps the Anchor, evidence, provenance, scope, activation revision, and id,
but changes `status` to `paused`. Paused Anchors remain visible and replayable and
are omitted from runtime guidance.

### Resume

Resume changes the same Anchor back to `active`. Its id and activation provenance
do not change.

### Remove

Remove publishes a full superseding snapshot without the target Anchor. The
append-only historical activation remains in DSH history, but replay does not
resurrect it.

### Clear

Clear publishes an empty authoritative Anchor snapshot. Its model-visible
control notice and subsequent runtime context explicitly state that earlier
Taskify constraint notices are superseded; append-only history is not deleted.

## Guidance vs Enforcement

Persistent Anchors are continued model guidance. They are not filesystem,
dependency, path, or write-time enforcement. STEP 3 adds no Git baseline,
mechanical guard, semantic diff audit, permission replacement, rollback, or
conflict/exception engine.

## Durable Representation

Taskify uses only DSH-known `UserMessage` data and known session events; it does
not add custom `taskify/*` events or parse model-visible XML as state.

Two strict `MessageSource` record types are used:

1. `activation` records contain bundle identity, exact-session binding,
   extracted `text/evidence`, and base/armed/activation revisions. An activation
   in Inbox reconstructs `request.armed`; the same identified message in a
   durable `user/message` reconstructs persistent active Anchors.
2. `state-update` records contain a complete, versioned authoritative Anchor
   snapshot plus validated operation metadata (`pause`, `resume`, `remove`, or
   `clear`). Inbox insertion is sufficient for the Host projection to apply the
   explicit user mutation immediately; later history consumption preserves the
   same record.

Replay folds raw `agent/inbox/spliced` and `user/message` events plus the live or
rebuilt Inbox. Operations are sorted by revision and stable identity. Later full
state snapshots supersede historical activation state, so pause, remove, and
clear survive cache deletion. Duplicate observations are idempotent. After a
cache rebuild, durability conservatively returns to `unavailable` because raw
events do not prove a historical flush result.

Lifecycle writes keep the established durability mapping:

- `flush() === true` → `confirmed`
- `flush() === false` → `unavailable`
- rejected `flush()` → `failed`

An already committed Inbox mutation is not falsely rolled back when flushing
fails.

## Runtime Context

Each live Agent receives at most one scoped dynamic
`agent.ctx.systemPrompt.context(...)` provider. It reads the latest Host
projection on every assembly and emits only active Anchors with the current
revision. Paused Anchors are excluded. An empty active set emits a short
superseding state so historical Taskify notices are not mistaken for current
authority.

The provider is installed again for Agent create/session-start, disposed with
the Agent, and keyed by exact session so one session cannot read another's
Anchors. Registration failure sets `runtimeContext.available = false`; the UI
warns that cross-turn guidance is unavailable instead of presenting it as fully
active. The first activation carrier can still guide its bound request.

For the first correctly bound request, pre-step never creates another contract.
The activation carrier remains the sole copy of its bundle. The runtime provider
excludes exact `text + evidence` entries already carried by that activation,
both while the request is still `armed` and for the first assembly after
activation. Older unrelated active Anchors remain in runtime context. This
avoids carrier/context/pre-step triple injection while preserving previously
active constraints.

## Client Behavior

The Anchor Dock renders `hostState.anchors`, independent of the current composer
draft and independent of request phase. Persistent chips therefore remain after
the original request is consumed, after draft edits, and after a component
remount followed by `getState()` hydration. Each chip exposes Pause/Resume and
Remove; the dock exposes Clear All. Client state is only a disposable cache of
Host snapshots and never fabricates lifecycle success.

STEP 3 intentionally does not add `watchState`. A single Client converges through
mount hydration, mutation responses, and one authoritative `getState()` refresh
when the existing conversation snapshot changes from `running: true` to
`running: false`. Revision conflict also triggers a fresh read. This lifecycle
refresh is not polling and does not run on render or keystrokes.

## Known Limitations

- Real DSH Web request materialization of `systemPrompt.context` and post-turn
  Client convergence have been verified against the pinned local rc.2 runtime.
- Concrete Web `agent.inject()` and persistence-backend restart/reload remain
  integration gates; cross-process confirmed durability depends on the real
  persistence provider returning `true` from `flush()`.
- There is no `watchState`; another Client may remain temporarily stale until its
  own lifecycle refresh, hydration, or mutation.
- There is no native Goal lifecycle or Goal-scoped inheritance.
- Forked/new sessions intentionally do not inherit exact-session Anchors.
- There is no automatic completion, conflict detection, exception system, or
  natural-language lifecycle mutation.
- There is no mechanical enforcement, Git baseline, semantic diff audit, or
  rollback.
- Lifecycle operations are serialized behind an idle request; an armed request
  must first activate or be invalidated.

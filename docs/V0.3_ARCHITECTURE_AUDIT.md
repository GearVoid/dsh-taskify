# DSH Taskify v0.3 前置架构审计

审计日期：2026-09-01  
仓库基线：`70ed6a8d81a908da6836c25f86ae1a12b798590e`（`main`）  
审计范围：只调查，不修改 runtime source，不修改生成产物 `client.js`，不修改 DeepSeek Harness upstream。

## Executive Conclusion

v0.3 的方向可以建立在当前 DSH 的 Session、Agent Inbox、agent-scoped runtime context 和 Typert Remote seam 上，但不能照搬“自定义 durable log event + native goal + file-mutation hook”这一整套假设。当前本地 API 只支持其中一部分。

最重要的结论如下：

1. 当前 Taskify 有两个互不相同的 process-local 状态源：Host 的 `activeAnchors` 和 Client 的 `sessions`。它们都不是 durable，且当前 Anchor 在第一次匹配的 `agent/pre-step` 被一次性消费。
2. `@deepseek-ai/dsh-session@0.1.0-rc.6` 提供 append-only Session log、replay seed、surface projection、fork 和 durability flush seam；真正落盘由另一个 persistence plugin 实现，核心包本身不持久化。
3. 外部插件可以调用 `session.append(...)`，但当前构建没有注册 downstream custom event type 的 API，`append(...)` 也不能为新事件写 `ignorable: true`。因此自造 `taskify/*` log-only event 虽能进入当前进程的 log，却不是安全的标准恢复格式。
4. 可以改用已知且持久的 `agent/inbox/spliced` / `user/message` 路径：用带 Taskify source 的 `UserMessage` 调用 `agent.inject(...)`，再用 `ctx.sessions.flush(agent.session)` 做 durability checkpoint。这条路径同时支持取消、resume 时 inbox 重建和进入 step 后的 durable history。
5. 持续注入的最佳 seam 不再是当前的一次性 `agent/pre-step`。本地 `@deepseek-ai/dsh-system-prompt@0.1.0-rc.6` 已提供 agent-scoped `ctx.systemPrompt.context(...)`；它每个 step 重新求值，并按其公开契约由 shipped loop 物化为 durable user-role runtime-context snapshot。`agent/pre-step` 仍适合做“待发送 Taskify 消息与真实 human draft 的绑定/筛选”，不应继续独自承担持续上下文。
6. 本地依赖图没有 Goal 实现包，也没有公开的 goal service/projection 类型。`KNOWN_SESSION_EVENT_TYPES` 中出现 `goal/change` 只说明这版 Session reader 知道该词汇，不构成可读取 goal id/revision/phase 的 API。
7. 有可靠的 durable `turn/end`、`step/end`、`tool/call`、`tool/result` 事件，以及完成前 awaited `agent/turn-stopping`。但没有本地可用的通用 tool-execution veto 或 file-mutation seam。未来只能先做 post-mutation mechanical verification，不能声称在写入前强制阻断。

## Current Architecture

### Host

`src/host/index.js` 中的 `TaskifyService`：

- 通过 Typert 暴露 `compile(request, signal)` 和 `invalidate(request)`。
- 使用当前 live agent 的 provider/model，找不到时回退到 deployment default model。
- 调用一次 LLM 完成 Anchor extraction；`compiler.js` 负责 JSON、provenance、modal strengthening 和 concrete-claim 校验。
- 成功后将 `{ anchors, acceptedDrafts }` 写入 `this.activeAnchors: Map<sessionId, ...>`。
- `invalidate()` 只删除这一内存 Map 项。
- `agent/pre-step` 在 downstream decision 为 `enter` 时，查找与 `acceptedDrafts` 精确匹配的 human user message，追加一条 plugin-sourced user message，然后立即删除 Map 项。

这意味着当前约束是：

- session-id scoped，但不是 DSH scope registration；
- process-local；
- send 前依赖 Client 及时 invalidate；
- 第一次匹配后一次性消费；
- 注入后只剩 model-visible XML 文本，没有可供 Taskify 恢复的结构化状态投影。

### Client

`src/shared/session-store.js` 在浏览器 bundle 内维护模块级 `Map<sessionId, TaskifySession>`。`TaskifySession` 管理 extracting/anchored/noop/error、AbortController、draft revision 和 UI listener。

`src/client/index.jsx`：

- 从 composer 读取 `draft`、`draftRev`、`phase` 和 reference occurrences；
- 通过 `remote.taskify.compile` / `invalidate` 调 Host；
- 在 `conversation.input.dock` 显示只读 chips；
- 在 draft 改动或 component unmount 时释放 Client state，并尝试 invalidate Host state。

Client 的 Anchor snapshot 与 Host 的 `activeAnchors` 没有 authoritative revision 或读取接口，连接重建、页面 reload 或多 Client 情况下可能分叉。

### Compiler and validation

`src/shared/compiler.js` 和 `src/shared/literal-lock.js` 的 v0.2 边界仍清晰：只分析当前 draft，最多 8 个 Anchor；每个 evidence 必须是当前 draft 精确子串；soft modality 不升级；明显具体代码 claim 不可凭空产生；受保护 literal 必须保持。

这些逻辑与 v0.3 的 state ownership 改造正交，应先保留，不应在架构迁移中顺便做 semantic diff audit 或 Minimal Diff Mode。

### Current tests

现有 45 个 Node tests 全部通过。它们覆盖 extraction、schema、literal lock、slash/reference policy、race/cancel、Client no-rewrite 和一次性 pre-step injection，但没有覆盖：

- Host authoritative projection；
- process restart / resume / fork / compaction；
- durability listener 缺失或 flush 失败；
- dynamic runtime context；
- goal integration；
- mechanical verification baseline；
- Host/Client revision convergence。

## Available DSH Seams

### 1. Session log and durability checkpoint

实际公开 API：

- `agent.session: Session`
- `ctx.sessions.get(id): Session | undefined`
- `session.append(type, data, opts?)`
- `session.events`
- `session.seq`
- `ctx.on('session/event', (session, event) => ...)`
- `await ctx.sessions.flush(session): boolean`

`session/event` 是 append 已提交后的同步 observer feed；observer 失败被记录并隔离，不能回滚 append。`flush()` 并行等待所有 persistence listeners：

- 返回 `true`：至少有一个 durability listener 参与并成功完成；
- 返回 `false`：当前 composition 没有 durability listener；
- reject：至少一个 listener 失败，但内存 append 已经发生，不能假装回滚。

因此“调用 `append`”只能称为 session-log durable intent；只有 `flush() === true` 才能在当前 composition 中确认到达一个持久化后端。

### 2. Replay, resume, fork, and surface reconstruction

实际公开 API：

- `Session.create(id, seed?, header?)`
- `Session.fromRestore(id, seed, header)`
- `ctx.sessions.create(id?, { seed?, meta? })`
- `ctx.sessions.prepare(id?, { seed, meta, seedSource: 'persistence' })`
- `ctx.sessions.fork(source, boundary?, childSessionId?)`
- `ctx.agents.resume({ resumeSessionId, agentOptions?, signal?, setup? })`
- `session.surface.nodes`
- `session.surface.replaceGeneration`
- `foldSurface(events)`
- `session.deriveMessages()` / `deriveEventMessage(event)`
- `session.header.parentSession` / `seedLength` / `firstLiveSeq`

限制：

- `dsh-session` 只提供 in-memory store；load/save 由未安装的 persistence provider 实现。
- `ctx.agents.resume(...)` 是 interface/factory seam；本地没有 Agent Loop/Persistence 实现，无法在此仓库独立做端到端 resume 验证。
- `fork()` 只接受 live source，boundary 必须是存在且不位于 open turn 内的 event seq。
- compaction 的实现包未安装；当前可确认的只有 surface `replace`、raw append-only log 和 `replaceGeneration` 机制。
- raw log 不删除被 compaction shadow 的事件。Taskify 的 durable projection若基于自己的 append-origin/source 事件折叠，可跨 surface replacement 恢复；不能只读 `deriveMessages()`。

### 3. Durable inbox

实际公开 API：

- `agent.inject(message)`：写入 `next-step`，不唤醒 idle agent；
- `agent.inbox.nextStep` / `nextTurn`；
- `agent.inbox.remove(messageId)` / `replace(...)` / `clear()`；
- 对应 durable `agent/inbox/spliced` event。

这是当前最适合保存“已经 Taskify、等待用户真正发送”的状态 seam：

- compile 成功后由 Host 创建一个 identified Taskify `UserMessage`，通过 `agent.inject()` 入队；
- source 中携带 Taskify schema version、constraint revision、scope、bound draft identity 和完整 Anchor snapshot；
- draft 改动或取消时由 Host 按 message id 调 `agent.inbox.remove(...)`；
- 每次 mutation 后 `await ctx.sessions.flush(agent.session)`；
- pre-step 仍验证 Taskify message 与同批 human message 的绑定，避免另一个 wake 误领待发送 constraints。

`MessageSourceMap` 是官方 merge-extensible sum，Session 的实际恢复校验接受非空的自定义 `source.kind`。这比自造未知 `taskify/*` Session event 安全，因为外层事件仍是 DSH 已知的 `agent/inbox/spliced` 和 `user/message`。

### 4. Agent-scoped persistent model context

`@deepseek-ai/dsh-system-prompt@0.1.0-rc.6` 公开：

```text
agent.ctx.systemPrompt.context({
  name,
  order,
  text: string | (assembleContext) => string,
})
```

其公开契约是：

- registration 归属 calling context 的 scope；通过 `agent.ctx` 注册只对该 agent 可见；
- provider 在每次 eligible prompt assembly 求值；
- dynamic contexts 与 system sections 分离；
- shipped loop 将完整 runtime-context snapshot 物化为 sourced user-role history；
- later snapshot supersedes earlier snapshot；
- `includeRuntimeContext: false` 或 scoped suppressor 可禁用模型可见 snapshot，但不会停掉拥有该状态的服务或 enforcement。

这比把 constraints 提升为 system prompt 更符合 Taskify 的 user-level instruction hierarchy，也比每个 `agent/pre-step` 手工追加重复消息更贴合“当前状态 snapshot”的语义。

需要在真实 Harness composition 做集成测试，因为 Agent Loop 实现不在当前本地依赖图中；当前能确认的是 system-prompt package 的公开 API/实现与它对 shipped loop 的契约，不能确认具体 loop 的 snapshot dedupe 细节。

### 5. Agent and Session lifecycle/events

可用的 live/durable信号：

| Seam | 时机 | Awaited / veto | Durable | 适用性 |
| --- | --- | --- | --- | --- |
| `agent/created` | agent 已配置并发布 | notification；同步 throw 可 veto publication | 否 | 安装/重建 scoped Taskify context |
| `agent/session-start` | 首轮前，source 为 startup/resume 等 | notification，不 gate | 否 | startup/resume hydration 后注入/检查 |
| `agent/pre-step` | inbox 已 claim，step 尚未进入 | waterfall，可 reject/replace batch | decision 进入后成为 durable messages | 绑定 human draft、过滤 pending Taskify message |
| `agent/turn-stopping` | completed turn 即将关闭 | awaited serial；可 `agent.steer()` 让 turn 继续 | 本身否 | mechanical verification 的最佳完成前 seam |
| `session/event: tool/call` | tool call 记录已提交 | observer，不能 veto | 是（有 persistence 时） | 观察，不是执行授权点 |
| `session/event: tool/result` | tool 已完成、结果已提交 | observer，不能 veto | 是（有 persistence 时） | 标记 dirty / 收集结果，不是 mutation guard |
| `session/event: step/end` | step 已关闭 | observer，不能 veto | 是（有 persistence 时） | 审计边界 |
| `session/event: turn/end` | turn 已关闭 | observer，不能 veto | 是（有 persistence 时） | 最终记录，不适合阻止 completed turn |

## Missing/Unsafe Assumptions

### Downstream custom session event is not safely replayable

`SessionEventMap` 在类型层允许 declaration merging，`session.append()` 在当前进程也会接受 JSON payload。但本地 `KNOWN_SESSION_EVENT_TYPES` 明确说明：

- 它只包含当前 Harness repository 构建时知道的事件；
- out-of-repo downstream plugin event 天然不在该集合；
- downstream event registration surface 尚未提供；
- persistence read 遇到未知且没有 `ignorable: true` 的事件必须拒绝恢复；
- `session.append()` 的当前参数又没有写入 `ignorable` envelope field 的选项。

所以现在直接实现 `session.append('taskify/constraints-changed', ...)` 会依赖不存在的恢复 API。不要这样做。

### Native Goal is not locally readable through a stable API

当前依赖图没有 Goal package、goal service、goal projection 或 goal-specific MessageSource 类型。唯一可见事实是 Session 已知事件集合中有字符串 `goal/change`。没有本地类型可说明其 payload，更没有可确认的：

- stable goal id；
- goal revision；
- goal phase；
- current/native goal getter；
- goal change subscription；
- goal-scoped Context key。

Taskify 不应：

- 解析 `/goal` 文本；
- 扫描 `goal/change` 的未声明 payload；
- 从 goal round 的 user message prose 反推状态；
- 自己实现一套平行 Goal；
- 假设 session id 等于 goal id。

当前应公开 `goalIntegration: { available: false }`，只实现 exact session scope。等本地基线出现官方 typed goal projection/getter 后，再增加可选 adapter。

### Remote event push cannot be assumed

Typert Client 有 `$on(event, listener)`，但只有 Host assembly allowlist 选择的、无 Scope 且返回 `void` 的事件能被 forward。当前 Taskify contribution 没有可验证的 Host event forwarding 配置，插件自身不能仅靠定义一个 Cordis event 就保证它跨 Host/Client。

因此 v0.3 不应把 authoritative state 同步建立在未经集成验证的 `$on('taskify/...')` 上。

### No reliable file-mutation veto

当前可用的 `tool/call` / `tool/result` 都是 durable observation event，`session/event` listener 失败被隔离。`tool/result.meta` 是 tool-private 且 optional；文档举例说某些 fs tool 可能放 contextual diff，不构成所有 mutation 的通用合同。

本地也没有 `dsh-tools` package 可审计，所以不能声称存在：

- before-tool execution veto；
- after-tool awaited guard；
- canonical changed-files result；
- file write/rename/delete event；
- mutation transaction / rollback。

### Presence in a generated vocabulary is not a callable capability

`KNOWN_SESSION_EVENT_TYPES` 还列出 compaction、goal、hook、plan、sandbox 等事件名。没有相应已安装实现包和公开服务时，这些名字只能用于安全读取兼容性判断，不能作为 Taskify 的实现依赖。

## Recommended State Ownership

### Authoritative source

Host owns all Taskify domain state。Client 只保存可丢弃的 Remote snapshot cache 和请求 UI 状态，不再拥有 session constraint truth。

建议的 Host projection key 是 exact `sessionId`，每个 snapshot 至少包含：

```text
schemaVersion
sessionId
revision
durability: confirmed | unavailable | failed
goalIntegration.available
pending constraint message identity (if any)
active constraints[]
scope: { kind: 'session', sessionId }
source draft binding / evidence
mechanical baseline metadata (only when enabled later)
last applied turn/step/surface generation
```

`revision` 必须由 Host 单调推进，Client mutation 带 `expectedRevision`，用 compare-and-swap 拒绝 stale update。Remote mutation 成功时返回完整新 snapshot，而不是只回 `{ ok: true }`。

### Durable representation

当前版本最安全的 durable representation 是 DSH 已知事件中的 Taskify-sourced identified `UserMessage`：

1. pending：`agent.inject(taskifyMessage)`，状态进入 durable `agent/inbox/spliced`；
2. cancel/replace：使用 `agent.inbox.remove/replace`，同样写 durable splice；
3. enter：pre-step 接受后，loop 写 durable `user/message`；
4. resume/replay：从 raw `session.events` 和重建后的 `agent.inbox` fold Taskify source；
5. compaction：projection 读取 raw append-only log，不把当前 surface 当 domain truth；
6. fork：事件虽然进入 seed，但 exact-session scope 必须检查消息中绑定的 session id；默认不把 parent session constraint 自动升级为 child scope。

Taskify source 应使用 merge-extensible `MessageSourceMap` 的独立 `kind`，并携带版本化、lossless-JSON 的结构化 snapshot。不要只解析模型可见 XML 文本，也不要复用其他核心事件类型承载 Taskify 私有数据。

每次 durable mutation 后必须调用：

```text
await ctx.sessions.flush(agent.session)
```

只有返回 `true` 才标记 `durability: confirmed`。返回 `false` 时功能可以保持 Host process-local，但 UI/Remote 必须准确暴露“当前 Harness 未配置持久化”，不能宣传 durable。

### Process-local projection

为性能可在 Host 维护 `Map<sessionId, projection>`，但它只是 raw log + inbox 的缓存：

- `agent/created` / `agent/session-start` 时重建；
- Taskify write path 同步更新；
- `session/event` 用于增量更新/失效；
- cache miss 可从 `agent.session.events` fold；
- cache 绝不成为唯一事实源。

## Recommended Host to Client Projection

继续使用现有 Typert Remote，而不是再建一套 Client store protocol：

- `getState({ sessionId }) -> TaskifyStateSnapshot`
- `compile({ ..., expectedRevision }) -> TaskifyStateSnapshot | error`
- `invalidate({ sessionId, expectedRevision }) -> TaskifyStateSnapshot | error`
- 后续 constraint lifecycle mutation 同样返回完整 snapshot。

如果需要 Host 主动变化（resume hydration、turn advancement、mechanical result）实时到 Client，推荐增加 cancellable long-poll Remote：

```text
watchState({ sessionId, afterRevision }, signal)
  -> next TaskifyStateSnapshot
```

它复用当前已验证的 direct Remote + AbortSignal seam，不依赖 Host event allowlist。Client mount 时先 `getState`，随后以 Host revision 循环 watch；断线重连后重新 `getState`。

只有在真实 Harness 集成测试确认 Taskify event 被 Host assembly forward 后，才可把 long-poll 替换为 `ctx.remote.$on(...)`。无论 transport 是什么，Host snapshot revision 都是唯一顺序依据。

## Recommended Goal Integration

当前实施策略：

1. 不实现 `/goal`，不解析 slash command 或 goal prose。
2. domain schema 预留一个 capability 字段，但只返回 `available: false`。
3. scope 第一阶段只允许 `{ kind: 'session', sessionId }`；不要伪造 goal id。
4. fork 默认不继承 exact-session constraints。若以后支持 goal scope，由官方 goal id 决定是否继承，而不是 parentSession 猜测。
5. 当且仅当本地安装的 DSH 提供 typed、read-only current-goal projection 时，再增加 adapter。最低要求是稳定的 goal identity 和可判定的 revision；phase 若不稳定则不要进入 Taskify correctness contract。

因此当前“Taskify 只读获取 native goal id/revision/phase”的答案是：不能通过已安装 API 安全完成；这是 goal-scoped constraints 的 blocker，但不是 session-scoped persistence 的 blocker。

## Recommended Continuous Constraint Seam

`agent/pre-step` 仍保留，但职责缩小：

- 对 pending Taskify message 与同批 human user message 做 exact binding；
- mismatch 时过滤/重新排队，避免 constraints 绑定到错误任务；
- 不再在 match 后删除所有 domain state；
- 不在每个 step 机械追加一条重复 contract message。

持续模型上下文改为：

- 在 `agent.ctx` 注册一个 `systemPrompt.context({ name: 'dsh-taskify:constraints', ... })`；
- provider 每个 step 从 Host authoritative projection 渲染当前 scope 的完整 constraint snapshot；
- 空状态返回空字符串；
- 保持 user-role runtime context，不转为 system section；
- resume 时在首个 assembly 前完成 scoped registration/hydration；
- 观察 `surface.replaceGeneration` 只用于 cache invalidation/测试，不用它做 domain revision。

如果真实 Agent Loop 集成测试不能证明 runtime-context snapshot 的 durable/replay 行为符合本地 package 契约，则回退到 pre-step re-injection，但必须用 Taskify revision + last-applied step/surface generation 去重，并明确它是兼容性 fallback。

## Recommended Mechanical Guard Seam

### 当前能安全实现的级别

未来第一版只能是 deterministic post-mutation guard：

1. activation 时由 Host 记录 repository baseline；
2. `session/event` 的 `tool/result` / `step/end` 只标记“可能需要复查”；
3. 在 awaited `agent/turn-stopping` 运行一次 deterministic check；
4. 若违反机械边界，调用 `agent.steer(...)` 让同一 turn 继续修复/解释；必要时可由已有 owner 调 `agent.cancel(...)`，但不能宣称已回滚文件；
5. 最终 `turn/end` 只记录结果，不作为阻断点。

这适合：

- 禁止修改某些明确路径；
- 只允许修改某些明确路径；
- 禁止新增依赖文件的机械集合检查；
- 禁止新增/删除文件等 syntactic policy。

它不适合：

- semantic diff audit；
- “不要破坏功能”等语义判断；
- 写入前强制阻断；
- 自动回滚。

### Git baseline，避免误判用户原有修改

绝不能把 `git diff HEAD` 直接当成 Agent 修改。正确基线是在 constraints activation 前对当前 worktree 做 snapshot，然后比较 activation 后的增量：

- 保存 repo root 与 HEAD oid；
- 保存 index 的 path/mode/stage/blob identity；
- 保存 activation 时已修改 tracked files 的 working-tree content hash 和 mode；
- 保存已有 untracked（必要时 ignored）path、content hash 和 mode；
- 保存 path 的存在/缺失状态，以检测新增、删除和 rename-like changes；
- 后续按同一规则重采样并比较两个 snapshot，而不是从当前 diff 中“减掉”旧 patch。

这样可避免把 activation 前已有的未提交改动算成 Agent 新改动。只保存初始 patch 再做文本相减不可靠：Agent 可能继续编辑同一 hunk。

仍然存在无法消除的归因限制：activation 后用户与 Agent 并发编辑同一 worktree 时，纯 Git snapshot 只能知道“发生了变化”，不能证明是谁改的。可靠归因需要隔离 worktree 或官方 file-mutation/tool execution attribution seam；当前都不存在。因此 guard 的措辞必须是“本次活动窗口内新增变化”，不能是“Agent 明确修改”。

baseline 若要跨 restart，必须跟随 Taskify durable state 保存；如果只放 Host Map，它只能 process-local。广域仓库 snapshot 还需要大小上限和失败策略，不能无限写入 session message source。

## Durable vs Process-local Capability Matrix

| Capability | 当前性质 | 说明 |
| --- | --- | --- |
| Taskify Client chips/controller | process-local | 浏览器模块 Map；reload/unmount 丢失 |
| Host `activeAnchors` | process-local | 第一次匹配后删除 |
| Taskify compile result | process-local | 当前未写 Session |
| 当前注入后的 XML user message | conditionally durable | loop 写入 Session；是否落盘取决于 persistence listener |
| `agent/inbox/spliced` pending Taskify message（推荐） | conditionally durable | 已知事件；mutation 后仍需成功 flush |
| Session raw events/surface/header | in-memory core + persistence seam | 核心不实现 storage；provider 决定跨进程 durable |
| replay/fork construction | available | seed/fork API 已存在；persistence load provider 未安装 |
| scoped prompt/context registration | process-local registration | resume 后要重建；其 materialized user snapshots 可 conditionally durable |
| Agent initiator/scope | process-local | 官方文档明确不跨 worker/process/restart |
| Typert Remote connection/subscription | process-local transport | authoritative truth 必须在 Host projection/session，不在连接 |
| native goal projection | unavailable | 本地无公开 API |
| tool/result / turn/end facts | conditionally durable | Session event，不能 veto 已完成动作 |
| file mutation attribution | unavailable | Git baseline只能做窗口增量，不识别 actor |

“conditionally durable”统一表示：Session event 已进入 append-only log，且只有 `ctx.sessions.flush(session) === true` 时，当前 composition 才确认有持久化参与者完成 checkpoint。

## Designs That Currently Depend on Non-existent DSH APIs

以下设计现在不应实现：

- 自定义 `taskify/*` log-only event 并假设标准 persistence 可 resume；
- 给 custom event 设置 `ignorable: true` 的 append option；
- 查询 `ctx.goals.current(...)`、`agent.goal` 或同类未安装 service；
- 依赖 stable native goal id/revision/phase；
- 监听 typed `goal/change` payload；
- 使用 goal-scoped Context/Remote lookup；
- 假设 compaction plugin 已安装或提供 Taskify callback；
- 依赖通用 tool-before/tool-after veto；
- 依赖 canonical file mutation event；
- 依赖所有 `tool/result.meta` 都包含 diff；
- 定义一个 Cordis event 后假设 Typert 自动 forward 到 Client；
- 从 persisted-but-unloaded session 直接 `ctx.sessions.fork(...)`；

## Risks

1. **Durability composition risk**：本地没有 persistence provider；必须用 `flush()` 的 boolean/exception 暴露实际能力。
2. **Custom source compatibility risk**：虽然 `MessageSourceMap` 官方可扩展且当前 runtime 接受未知 kind，仍需在真实 Web transcript、persistence load 和 compaction 中做集成测试。
3. **Runtime-context loop risk**：system-prompt package 在本地，Agent Loop 不在；snapshot materialization/dedupe 必须在目标 Harness 复核。
4. **Pending message misbinding**：`agent.inject()` 可能被另一个 wake 先 claim；必须由 pre-step 校验 bound human message，不能仅凭 next-step FIFO 假设。
5. **Append/flush split failure**：append 已提交后 flush 可能失败；需要 idempotent revision/source message identity 和明确的 degraded state，不能尝试删除 append-only history。
6. **Projection drift**：`session/event` observer 失败不会阻止写入；projection 必须可从 raw log/inbox完全重建。
7. **Fork leakage**：seed 会携带 parent Taskify events；exact-session scope 必须过滤 parent-bound state。
8. **Compaction visibility**：surface replacement 会改变 model history；domain fold 必须读 raw events，runtime context 负责重发表当前 snapshot。
9. **Client staleness**：未验证 event forwarding；使用 snapshot + revision + cancellable long-poll，不能只靠本地 React store。
10. **Mechanical attribution**：Git baseline 不区分 activation 后的用户并发修改；只能报告活动窗口增量。
11. **Repository size**：全仓库 hash baseline 可能昂贵且 session payload 过大；实施时要有 scope、上限和 fail-closed/fail-visible policy。
12. **Instruction hierarchy**：不要把用户约束注册为 system section；应保持 user-role runtime context。

## Proposed Implementation Order

### Phase 0 — Capability pinning

1. 为本地 rc.6 public seams 写 contract tests：`agent.inject`/Inbox、Session append/flush、raw replay fold、systemPrompt.context、pre-step、turn-stopping。
2. 在实际 DSH Web composition 验证 persistence listener、Agent Loop runtime-context snapshot、Client Remote mount。
3. 明确 feature flags：`persistenceAvailable`、`runtimeContextAvailable`、`goalIntegrationAvailable=false`、`mechanicalGuardLevel='post-mutation'`。

### Phase 1 — Host authority without behavior expansion

1. 定义 versioned Taskify state/source codec 和 Host projection。
2. 增加 `getState`、revisioned mutation result；Client 改为 Host snapshot cache。
3. 保持现有 extraction、只读 chips、no rewrite、no auto-submit。
4. 删除 Client/Host 双重 authoritative Anchor state。

### Phase 2 — Durable pending and active constraints

1. compile 成功后创建 Taskify-sourced identified UserMessage 并 `agent.inject()`。
2. invalidate/cancel 用 Inbox API 操作 message identity。
3. 每次 mutation 后 `ctx.sessions.flush()`，准确处理 true/false/reject。
4. 从 raw events + inbox 实现 deterministic fold；覆盖 restart/resume seed tests。

### Phase 3 — Scoped persistent model context

1. 在 agent scope 注册 `systemPrompt.context` provider。
2. pre-step 只负责 bound-draft claim validation。
3. 验证多 step、resume、fork exact-session filtering 和 surface replacement。
4. native Goal 保持 capability-unavailable，不做替代实现。

### Phase 4 — Authoritative Client convergence

1. Client mount/session switch 先 `getState`。
2. mutation 采用 expectedRevision/CAS。
3. 用 cancellable `watchState` long-poll 接收 Host 主动 revision；若真实 Host event forwarding 被证明可用，再换为 `$on`。

### Phase 5 — Minimal deterministic mechanical verification

1. 只实现 path/file-set 等 mechanical policies。
2. activation 时记录 pre-existing dirty/untracked baseline。
3. tool/step events 只置 dirty，`agent/turn-stopping` 做 awaited check。
4. violation 时 steer remediation/说明；不做 semantic audit、不自动 rollback、不宣称 write-time blocking。

### Phase 6 — Documentation and generated Client bundle

1. 更新测试、README 和 compatibility matrix。
2. 最后运行 build 生成 `client.js`，只接受由 source build 产生的差异。
3. 保持无新增第三方 dependency，不修改 DeepSeek Harness upstream。

# V0.3 Capability Pinning

## Scope

This document records STEP 0.5 contract evidence for the locally installed
DeepSeek Harness packages. It is subordinate to
`docs/V0.3_ARCHITECTURE_AUDIT.md` and does not start the v0.3 runtime migration.

The executable fixtures use only public rc.6 exports and known DSH session
events. They do not add a Taskify state schema, custom `taskify/*` session
events, persistence fallback, mechanical guard, or runtime behavior.

## Seam Evidence

### 1. `agent.inject` / Inbox — PARTIAL

The installed `Inbox` implementation was exercised directly with a real
`Session`:

- an identified, frozen `UserMessage` with `source.kind: "dsh-taskify"` enters
  the `next-step` projection;
- nested lossless-JSON source payload is preserved in the logged snapshot;
- the only emitted event is known `agent/inbox/spliced`;
- `remove(messageId)` deletes exactly the live identity and records a canceled
  splice;
- `replace(oldId, replacement)` adopts the replacement message's identity,
  publishes the old message as discarded and the replacement as inserted, and
  returns `false` if the old identity is no longer pending;
- reconstructing `Inbox` from `Session.fromRestore(...)` replays the same
  pending identity.

The concrete Agent implementation is owned by an Agent Loop package that is
not present in this repository's installed dependency graph. Therefore the
test does **not** create a fake Agent and does **not** claim that the actual Web
`agent.inject(message)` delegation has been verified. The remaining Web test
must show that `agent.inject(taskifyMessage)` appends that exact identified
message to the next-step Inbox before STEP 1 treats injection as integrated.

### 2. Raw session event fold — PASS

The pure prototype consumes only `session.events` entries of these known types:

- `agent/inbox/spliced`
- `user/message`

It recovers structured payload from the message source rather than parsing
model-visible text. The contract distinguishes:

- `insert`: a Taskify message became pending;
- `claim`: the Inbox removed it for a step, without cancellation outcome;
- `enter`: the same identified message reached `user/message`;
- `duplicate`: a repeated `user/message` with the same identity is recorded but
  does not become a second domain record;
- `replace`: an Inbox splice removed one Taskify identity and inserted another;
- `remove`: a canceled splice removed the pending identity.

Unrelated user messages are ignored. A Taskify `user/message` shadowed by a
valid DSH surface replacement disappears from `deriveMessages()` but remains
recoverable from raw events. This confirms that the current surface cannot be
the future domain truth.

The prototype is not the v0.3 schema. STEP 1 still has to define revision,
status, idempotency, corruption handling, and fold output as Host-owned domain
types.

### 3. `ctx.sessions.flush` — PASS

The tests use the real `SessionStore` and establish the only permitted mapping:

| `flush(session)` outcome | Taskify durability claim |
| --- | --- |
| resolves `true` | `confirmed` |
| resolves `false` | `unavailable` |
| rejects | `failed` |

When no persistence listener participates, process-local Inbox/session state
remains usable but is not cross-process durable. When a listener rejects, the
already accepted `agent/inbox/spliced` event and live Inbox mutation remain.
The classifier reports failure and performs no fake rollback of append-only
history.

A real DSH Web deployment still must show `true` with its configured
persistence backend and must reload the resulting session in a new process
before cross-process durability is claimed.

### 4. `systemPrompt.context` — PASS locally

The installed public API supports the intended form:

1. create/use the exact Agent scope;
2. call `agent.ctx.systemPrompt.context(...)` through that scoped context;
3. provide a dynamic `text` callback;
4. assemble with the same Agent scope.

The test proves that the callback re-reads changed state on every scoped
assembly, can return an empty string, does not appear in an unscoped/global
assembly, and contributes through `assembly.contexts` rather than
`assembly.sections`. `renderContextSnapshot()` omits an empty contribution.

**LOCAL CONTRACT VERIFIED**

**REAL DSH WEB INTEGRATION REQUIRED**

The concrete Agent Loop/request builder is not installed here. This repository
cannot independently prove how the context is materialized as a user-level
request snapshot, when its snapshot is logged, or whether unchanged snapshots
are deduplicated across steps. A Web integration test must verify those points
before persistent constraint injection is considered complete.

### 5. `agent/pre-step` binding — PASS locally

The contract registers the test-only binding handler on the real Cordis/DSH
waterfall dispatcher. It proves that a handler can:

- await `next()` and inspect the downstream `enter.messages` decision;
- distinguish a human message by `role: "user"` plus `source.kind: "user"`;
- distinguish a Taskify-sourced user message;
- retain an exact `boundDraft` match;
- filter a mismatch before returning the model-entry decision;
- reject a false match where the same text came only from another plugin.

The prototype holds no map, revision, or constraint state. Long-term ownership
therefore stays with the future Host projection; pre-step remains only an exact
binding boundary.

The final DSH Web request path should still verify handler ordering and prove
that the filtered decision is exactly what the request builder consumes.

### 6. `agent/turn-stopping` — PARTIAL

Using the installed `agentEvents(...).serial(...)` dispatcher, an async
`agent/turn-stopping` handler completes before dispatch resolves. This pins the
awaited event contract.

The Agent Loop is absent, so the repository cannot prove either of the
behavioral statements that matter to STEP 5:

- the dispatch happens immediately before the completed turn commits its close;
- `agent.steer(...)` causes the actual loop to re-read Inbox and run another
  step.

No fake `steer` implementation was used. This seam remains an explicit Web
integration requirement and is not yet approved as a deterministic mechanical
guard boundary.

## Integration Gates

Before claiming the corresponding end-to-end behavior, run these tests in the
real DSH Web composition:

1. Call concrete `agent.inject()` with an identified Taskify message and observe
   the same identity in `agent.inbox.nextStep` and raw `agent/inbox/spliced`.
2. With the real persistence plugin enabled, require `ctx.sessions.flush()` to
   return `true`, restart the process, resume the session, and compare the raw
   fold result.
3. Register Taskify context through the exact Agent context and inspect the
   actual model request plus logged context snapshots over changed, unchanged,
   and empty states.
4. Send matched and mismatched human/Taskify pairs through a real turn and
   confirm pre-step output is the request input.
5. At turn stopping, call real `agent.steer()` and confirm another step occurs
   before the same turn closes.

These gates validate external composition. They must not be replaced with
Client `localStorage`, custom Taskify events, XML parsing, or a mocked Agent
Loop.

## Blockers and Entry Decision

No new blocker was found for beginning the narrowly scoped Host Authority
migration. The raw message/event path, deterministic fold feasibility, flush
result semantics, scoped runtime-context registration, and exact pre-step
binding contract are sufficiently pinned for STEP 1 design and implementation.

Entry is conditional on preserving these limits:

- do not claim cross-process durability unless flush resolves `true` and the
  real backend reload test passes;
- keep the concrete `agent.inject` and Agent Loop context behavior behind a Web
  integration gate;
- do not use `agent/turn-stopping` for STEP 5 enforcement until steer
  continuation is verified;
- do not add native Goal integration: the installed graph still exposes no
  supported Goal read service with stable goal id/revision/phase;
- do not design a mutation veto or rollback around observation-only tool/session
  events.

The last two items remain capability absences, not STEP 1 blockers.

## Explicit Non-Changes

This step did not modify runtime source, Host behavior, Client behavior,
compiler semantics, persistent Anchor behavior, package dependencies, or the
generated `client.js`. It did not implement Host Authority, Persistent Anchors,
Goal integration, a mechanical guard, Git baseline capture, Minimal Diff Mode,
semantic diff auditing, write-time enforcement, or rollback.

# V0.3 STEP 2 — Durable Pending Representation and Replayable Host State

## Scope

STEP 2 changes the STEP 1 Host projection from a process-local authority into
a cache over a reconstructable DSH-known representation. It deliberately keeps
the v0.2 one-shot lifecycle:

```text
compile -> armed -> exact bound human prompt -> consume -> idle
```

**STEP 2 does not implement Persistent Anchors.** It does not use
`systemPrompt.context`, add cross-turn guidance, introduce `taskify/*` session
events, integrate native Goal, add a mechanical guard, or make the Client an
authority.

## Durable Representation

A successful non-empty compile creates one identified DSH `UserMessage` and
passes it to the concrete live Agent through `agent.inject(message)`. DSH places
that message in the next-step Inbox and records the mutation as the known
`agent/inbox/spliced` session event.

The same message has two bounded responsibilities:

1. its `content` is the existing `buildConstraintContract(anchors)` output for
   the one correct model request;
2. its structured `source` is the lossless Taskify domain carrier used for
   replay.

Pre-step does not manufacture a second contract message.

The dependency-free strict codec in `src/shared/source.js` defines source
schema version 1. It contains:

- `kind: "dsh-taskify"` and `schemaVersion: 1`;
- exact `sessionId`;
- deterministic `bundleId`;
- Host-assigned `baseRevision` and `armedRevision`;
- Host-assigned `requestId`;
- exact `boundDraft`, `sourceDraft`, and their deduplicated accepted binding
  values;
- the validated Anchor snapshot.

Exact drafts are stored instead of hashes. This keeps slash-command semantics
identical to STEP 1, avoids digest ambiguity in the domain format, and needs no
new dependency. The codec caps draft, id, Anchor count, Anchor text, and
evidence sizes. It rejects unknown fields, malformed payloads, inconsistent
operation identities, unsupported versions, and wrong-session sources.

The source is domain truth. Recovery never parses model-visible XML or other
message content.

## Host Projection Is a Cache

`TaskifyStateProjection` remains the only Host-side state interface used by the
Remote and Client, but its Map is now disposable. The Host hydrates from the
live Agent on `agent/created` and `agent/session-start`. Relevant
`session/event` observations mark the session cache dirty. `getState` rebuilds
on a cache miss or dirty entry using the exact live Session and Inbox.

The projection refuses revision rollback. This preserves a newer in-flight
process-local state when raw known state is necessarily older, such as while an
LLM extraction is pending.

The `pending` phase remains ephemeral by design. Abort controllers, streaming
state, and unfinished model computation are not written into Session history.
The durable/rebuildable phase begins only after a non-empty extraction has
created its Inbox carrier.

An empty successful extraction retains the STEP 1 visible no-op snapshot with
`carrier: null` and `durability.status: "unavailable"`. There is no constraint
bundle to persist in that case.

## Rebuild Algorithm

`src/shared/projection.js` folds raw `session.events` plus the live or replayed
Inbox. It uses only known rc.6 events:

- `agent/inbox/spliced` reconstructs insertion, claim, replacement, requeue,
  and exact cancellation/removal;
- `user/message` proves that an identified Taskify carrier entered transcript
  history and was consumed.

For each strictly valid exact-session bundle, operation revisions come from
the structured source rather than listener call count:

```text
carrier pending in Inbox                 -> armedRevision, armed
carrier entered as user/message          -> armedRevision + 1, idle
carrier removed/canceled from Inbox      -> armedRevision + 1, idle
claim followed by same-identity requeue  -> armedRevision, armed
```

The highest deterministic operation revision wins. Replaying duplicate events
or rebuilding the same input twice cannot allocate another revision. Invalid,
unsupported, unrelated, and wrong-session sources are ignored. A child rebuild
therefore ignores seeded parent Taskify sources whose embedded `sessionId`
still identifies the parent.

Raw append-only history cannot resurrect a removed or already consumed
one-shot bundle. The fold does not use `deriveMessages()`, current surface
history, Client cache, or contract content.

## Compile and Injection Semantics

For a non-empty valid result, the Host performs:

```text
ephemeral pending
-> create strict Taskify source and identified UserMessage
-> agent.inject(message)
-> armed projection with exact message/bundle/request identity
-> ctx.sessions.flush(agent.session)
```

If no live Agent or callable `agent.inject` exists, the compile fails visibly,
clears ephemeral pending state, and reports unavailable durability. If
injection throws, the Host checks the exact message identity in the live Inbox:
an already committed append is retained; an uncommitted injection fails. It
never silently claims replayability and never falls back to Client storage.

Replacing an already armed compile first removes the old exact carrier. A
failed exact removal does not delete any other Inbox item and fails visibly.

## Flush Semantics

After a committed injection, safe requeue, or exact invalidate removal, the
Host calls `ctx.sessions.flush(session)` and records the observed checkpoint
status without allocating a domain revision:

| Result | Snapshot status | Meaning |
| --- | --- | --- |
| `true` | `confirmed` | At least one persistence participant completed this checkpoint. |
| `false` | `unavailable` | Session-memory behavior works, but persistence is not confirmed. |
| rejection | `failed` | The Inbox/session mutation already committed; its checkpoint failed. |

A rejection never rolls back or deletes the committed history. Durability
status is checkpoint metadata, not a lifecycle transition.

Rebuild conservatively reports `unavailable` because rc.6 raw events contain no
durable checkpoint-result event and STEP 2 forbids a custom Taskify event. A
real resumed carrier still rebuilds correctly, but the prior in-process flush
return value cannot be reconstructed from raw history alone.

## Binding and One-Shot Consumption

At `agent/pre-step`, Taskify inspects claimed Taskify messages after downstream
waterfall processing and compares the structured source binding with exact
human-source text in the proposed request.

On an exact match, the existing carrier is allowed unchanged. It is the only
constraint message in the request. Host state moves `armed -> idle` once. A
later step receives no automatic Taskify message. Taskify marks this immediate
consume transition `unavailable`: at pre-step time the later `user/message`
append has not happened yet, so Taskify cannot truthfully checkpoint or confirm
that future event itself.

On mismatch, Taskify filters the carrier from that request, reinjects the same
identified message, checkpoints the requeue, and keeps the same bundle,
revision, and armed state. It does not create another Anchor bundle or let a
plugin-origin message impersonate the bound human prompt.

Malformed, unsupported, stale, and wrong-session Taskify messages are never
allowed into a request as current Taskify constraints.

## Invalidate

Invalidate remains a Host CAS mutation. For an armed carrier it resolves the
live exact Agent, calls `agent.inbox.remove(active.carrier.messageId)`, flushes
the committed removal, and then advances to idle exactly once. A missing or
wrong identity fails visibly and cannot remove an unrelated Inbox message.

On replay, the cancellation splice wins over the older insertion and rebuilds
idle.

## Locally Verified

The repository tests use the actually resolved rc.6 `Session` and `Inbox`
implementations and verify:

- strict source validation, bounds, versioning, and exact-session rejection;
- identified carrier injection and lossless structured source preservation;
- exact contract content and absence of duplicate pre-step injection;
- `flush` true, false, and rejection behavior;
- committed-after-throw injection behavior without false rollback;
- exact invalidate removal and wrong-id safety;
- current Inbox carrier rebuilding armed;
- consumed and removed carriers rebuilding idle;
- deterministic repeated replay and duplicate observation;
- cache clear followed by Host rebuild;
- wrong-session/parent sources, malformed data, and unrelated events ignored;
- exact correct binding, mismatch filtering, and same-identity requeue;
- first-request-only consumption and no second-step reinjection;
- `goalIntegration.available` remains false.

## Requires Real DSH Web Verification

This repository does not include the full DSH Web composition or a persistence
provider. The following remain integration checks, not completed claims:

- concrete `agent.inject()` in the composed Web runtime;
- actual next-step Inbox ordering under concurrent wake/steer activity;
- mismatched-wake requeue through the real Agent Loop;
- `flush === true` with a real persistence plugin;
- process restart and persistence load;
- Agent resume and restored Inbox publication order;
- pre-step output reaching the actual model request exactly once;
- Taskify custom MessageSource survival through the deployed persistence and
  compaction pipeline.

Replay logic is verified locally. Cross-process persistence requires real DSH
Web integration with `flush === true`.

## Known Limitations

- A compile that has not completed extraction is process-local and is not
  resumed.
- A successful empty/no-op snapshot has no Inbox carrier and is process-local.
- Prior `confirmed`/`failed` checkpoint status is not encoded in raw events, so
  rebuild reports `unavailable`.
- A crash after an Inbox claim but before pre-step can requeue or transcript
  entry leaves only the claim event; the fold conservatively treats that bundle
  as no longer pending. End-to-end Agent Loop behavior still needs Web testing.
- No local test proves actual cross-process persistence, restart, resume, or
  compaction behavior.
- Host-to-Client state remains request/response Remote snapshots; STEP 2 adds
  no watchState/server push.

## Explicitly Not Changed

- Extraction remains “Extract, don't invent.”
- Compiler and literal-lock philosophy are unchanged.
- No Persistent Anchors or cross-turn automatic guidance exists.
- No `systemPrompt.context`, watchState, Goal integration, `/goal` parsing,
  structured scope, Minimal Diff, mechanical guard, Git baseline, semantic
  audit, automatic rollback, new dependency, or upstream modification exists.
- The Client remains a disposable snapshot cache and cannot write domain
  history directly.
